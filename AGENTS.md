# go-mistral

Unofficial Go client for the Mistral AI REST API, generated with oapi-codegen. If you only want to use the client from an agent, read [.agents/skills/go-mistral/SKILL.md](.agents/skills/go-mistral/SKILL.md) instead; this file is about changing the code.

## Architecture

Generation pipeline, declared in `gen.go` and run by `make generate`:

1. `scripts/fetch-spec.sh` downloads `openapi.yaml` from `https://docs.mistral.ai/openapi.yaml` into `api/`.
2. `scripts/patch-spec.sh` writes `api/openapi.patched.yaml` with every `const: true` and `const: false` line dropped, because one of them generates a type name that collides with a component schema.
3. `internal/cmd/patch-spec` rewrites `api/openapi.patched.yaml`: it moves the schemas nested in local `$defs` blocks into `components/schemas`, which kin-openapi cannot resolve otherwise, and gives a query parameter its own Go name (`x-go-name`) when an earlier parameter of the same operation maps to the same field.
4. oapi-codegen runs with `config.yaml` on the patched spec.
5. The result is `client.gen.go`: models, `Client` and `ClientWithResponses` in package `mistral`.

## Stack

- Go 1.26.10, one package at the module root.
- oapi-codegen v2 and golangci-lint as `go tool` dependencies.
- Runtime: `github.com/oapi-codegen/runtime`.

## Layout

- `client.gen.go`: generated client and models.
- `gen.go`: package doc and the `go:generate` steps.
- `config.yaml`: oapi-codegen config.
- `client_test.go`, `example_test.go`: tests against an `httptest` server, and the README example.
- `scripts/`: spec fetch and patch, lint and security scan scripts.
- `api/`: downloaded spec, gitignored.
- `vendor/`: committed, regenerated by `make dep`.

## Dev workflow

Everything runs in the `Dockerfile.dev` image. You need Docker and Make.

```bash
make dep       # go mod tidy + go mod vendor
make generate  # download the spec, patch it, regenerate client.gen.go
make lint      # shellcheck, shfmt, go fix, golangci-lint
make test      # go test -race
make sec       # gitleaks, govulncheck, semgrep
```

## Project-specific landmines

- `make generate` always downloads the current upstream spec, so a regeneration can pull in unrelated upstream changes. Method names follow operation IDs, so an upstream rename renames a method. Review the `client.gen.go` diff before committing.
- Upstream spec problems come back on every download. Fix them in `scripts/patch-spec.sh`, never in `client.gen.go`.
- Message lists and message content are union types. The README and the skill show `From...` calls by variant name; check those names after a regeneration.
- `.github/workflows/regen.yml` regenerates the client every day and releases the result. When the checks fail, Claude edits the repository to fix them, but a fix may not touch the paths listed under `fix_protected_paths` in that workflow: the workflows, the Makefile, `AGENTS.md`, `.agents/rules/`, the lint, security and spec download scripts and their configs. A problem that needs a change there fails the run and needs a manual fix.
